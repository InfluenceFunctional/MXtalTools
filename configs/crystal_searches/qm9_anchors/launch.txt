qm9_anchors -- cluster launch sequence. 50 disjoint QM9 chunks, SG2 Z'=1, house ELJ recipe.
============================================================================================

WHAT RUNS
  50 array tasks, one per chunk. 9750 standardized molecules total, 195 per chunk, x 10
  random inits = 1950 structures = 2 batches of 1000, two rprop stages (450 compress + 50
  relax). Chunks are disjoint and write distinct outputs, so tasks need no coordination.
  The qm9c100k tag counts CRYSTALS, not molecules: 9750 x 10 inits = 97,500 anchors.

  Measured on job 15745882_0: 2.99 samples/s, so ~11 min/chunk. Header asks 1 hour.

CONFIGS
  ./qm9c100k_chunk<k>.yaml, k = 0..49, carrying /scratch paths -- these are cluster configs
  and will not resolve on the Windows box. Regenerate with:

    python make_chunks.py --chunks 50 --num-samples 10 --tag qm9c100k \
        --mol-stem qm9_cluster_mols \
        --mol-dir /scratch/mk8347/data/crystal_datasets/conditional/priors \
        --out-dir /scratch/mk8347/data/crystal_datasets/conditional/anchors \
        --dest .

  --num-samples 10 and --tag qm9c100k are NOT the script defaults (50 / qm9cluster). Omitting
  either silently produces a different, wrongly named set.

  Same command with --mol-dir/--out-dir under D:/crystal_datasets/conditional rebuilds a
  local-path set, if a chunk ever needs to run on the workstation.

  The three non-chunk yamls here (qm9_sg2_anchors_elj, its smoke, the b1000 timing probe)
  are the local runs already on disk and still point at D:. They are not part of the array.

  Then the rest:
    sbatch --array=1-49 configs/crystal_searches/qm9_anchors/submit_chunks.sbatch

RESUME
  force_restart_run is false and run_search torch.saves after every batch, so resubmitting a
  killed task picks up at its cursor -- a chunk that died after one batch restarts at 900 or
  1000, not 0. Caveat: batch_idx is reconstructed as (cursor // batch_size) - 1, so a task
  that hit OOM and shrank its batch re-seeds inits off a different index on resume. The
  partition and the outputs stay correct; only the random inits of resumed batches differ.

READING A LIVE LOG -- job 15745882
  A running task looks dead. tqdm rewrites one line with \r, so cat shows the bar frozen at
  the last COMPLETED batch, and every task in an array sits at the same point at the same
  time -- 26 identical-looking .out files is what a healthy array looks like mid-flight.
  Check the outputs, not the log: a finished chunk is 1950 crystals at ~3.0 KB each, so
  ~5.7 MB. A task stuck after one batch would be ~2.8 MB.

  That job also shows the bar at 900/1950 where a clean first batch prints 950, so batch
  1000 took one CUDA OOM and the handler cut it to 900. Absorbed, chunks completed. It costs
  one wasted 500-step optimisation per chunk; batch_size 900 in the configs would avoid it.
  gpu:1 and 32G are what that job ran on, so they stay.

CHECK
  Expect 50 files, /scratch/mk8347/data/crystal_datasets/conditional/anchors/qm9c100k_chunk<k>.pt.
  A short file means the task died mid-run rather than that the chunk was small -- compare
  len(torch.load(...)) against 10 x (molecules in that chunk).
